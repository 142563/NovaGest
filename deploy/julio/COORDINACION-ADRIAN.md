# Coordinación de despliegue con Adrian

Este documento fija el contrato entre el backend NovaGest y la automatización de despliegue (DES9–12). También anota las dependencias de acceso y publicación (DES19–23). ## Contrato del backend

- **Rutas:** la API conserva el prefijo `/api` (por ejemplo, `POST /api/auth/login` y `GET /api/tramites`). La salud pública es `GET /actuator/health`, devuelve estado sin detalles internos. El proxy debe enviar ambas rutas al backend conservando sus paths; no hay `context-path` configurado. En producción, Swagger/OpenAPI está desactivado.
- **Puertos:** la imagen documenta el puerto de contenedor `8080`; no define otro `server.port` ni `server.address`. El contrato operativo acordado en el tablero es publicar el contenedor solo en loopback del host: producción `127.0.0.1:8080 -> contenedor:8080`, staging `127.0.0.1:8081 -> contenedor:8080`. El proxy de Nginx de Julio puede apuntar a esos puertos. Preservar el sitio `navcontrol` que usa el puerto público `443` y su upstream `9080`.
- **Perfil y variables para producción:** fijar explícitamente `SPRING_PROFILES_ACTIVE=prod`; el perfil por defecto del backend es `dev`. Pasar `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` para PostgreSQL externo, más `JWT_SECRET` (al menos 32 bytes UTF-8, clave aleatoria y privada). Definir también `COMPROBANTES_DIR=/data/comprobantes`. No poner valores de secretos en el repositorio, la imagen, argumentos públicos ni logs. El `.env` local está ignorado y excluido de la imagen.
- **Base de datos:** `docker-compose.yml` es el entorno de desarrollo: arranca PostgreSQL 17 y la app con perfil `dev`, conecta la app al servicio `db` y publica los puertos del host. No usar ese compose como definición de producción. En producción la app conecta a una instancia PostgreSQL externa mediante `DB_*`. Hibernate valida (`ddl-auto=validate`) y Flyway aplica migraciones al arrancar; en `prod`, `clean` está deshabilitado y se valida cada migración. La cuenta de aplicación necesita los permisos acordados con DBA para aplicar las migraciones.
- **Comprobantes y respaldo:** los archivos se guardan en disco bajo `COMPROBANTES_DIR`; la base guarda nombre generado, tipo, tamaño y hash, pero no el contenido. Montar un volumen/directorio persistente del host en `/data/comprobantes` y respaldarlo junto con la base, con una política de restauración coordinada. La imagen crea esa ruta para el usuario sin privilegios `novagest`; comprobar que el volumen montado permita escritura a ese usuario. El límite de carga es 5 MB por comprobante (6 MB por solicitud).
- **Health y acceso:** `/actuator/health` está permitido sin token y `show-details=never`; los demás endpoints exigen autenticación salvo registro/login/refresh. Una respuesta `UP` debe comprobarse después del arranque y tras el despliegue; el estado incluye las dependencias de salud configuradas por Spring Boot.

## CI, proxy y pendientes de coordinación

- **CI confirmado:** `.github/workflows/ci.yml` corre con pull requests a `develop`/`main` y pushes a esas ramas. Usa Java 21, ejecuta `./mvnw -B clean verify` con Testcontainers y conserva artefactos de evidencia. No construye ni publica una imagen Docker, no despliega y no declara secrets de CI. Adrian es dueño de automatización; DES9–12 deben añadir el flujo de imagen/despliegue, credenciales de forma segura, selección de rama/entorno, y una comprobación de salud/rollback que respete el contrato de puertos y datos persistentes.
- **CORS:** no hay configuración CORS ni `@CrossOrigin` en el código. Una interfaz servida desde otro origen no podrá llamar a la API desde navegador sin una decisión y configuración explícitas. Preferir una publicación same-origin mediante el proxy; si staging o frontend usan orígenes distintos, acordar la lista exacta de orígenes antes de habilitarla. No abrir CORS con comodín para una API que usa credenciales/tokens.
- **Headers del proxy:** el proyecto no configura explícitamente el manejo de `Forwarded`/`X-Forwarded-*`. Bitácora toma `getRemoteAddr()` deliberadamente y documenta que detrás de proxy registra la IP del proxy; no confía en `X-Forwarded-For`. El proxy debe enviar `Host` y esquema correctos para el tráfico normal y Adrian/Julio deben validar en staging cualquier comportamiento que dependa de HTTPS o de esos headers. No usar una IP reenviada por el cliente como identidad auditada.
- **Migraciones y permisos:** hay migraciones Flyway hasta V10. V1 es línea base sin tablas; comentarios de V9 y V10 las describen como borradores para revisión DBA. Coordinar revisión/aprobación de DBA y privilegios de la cuenta antes de que un despliegue aplique cambios a la base compartida.
- **Coordinación de tareas:** Julio gestiona Linux/SSH/firewall/Nginx y la publicación loopback; Adrian mantiene la automatización. DES19–23 (accesos) deben dejar claro quién administra credenciales y quién las rota, sin compartir valores secretos por chat ni en el repo.
